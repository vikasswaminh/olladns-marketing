Designing scoped API keys for agents

Engineering May 15, 2026 5 min read by olladns Engineering

CI pipelines, SIEM connectors, and AI agents all need API access, but they should not share the same key. Here is how we built scoped tokens that keep each workload inside its lane.

Key Takeaways

1

Traditional API Keys Are Too Powerful

A single long-lived API key for an agent can leak, be replayed, or be used beyond its intended scope. Scoped keys reduce blast radius.

2

Scope Keys to a Single Actor and Use Case

Each key should be issued for a specific agent, service, or workflow with tightly limited permissions, expiration, and allowed actions.

3

One Auth Surface, Many Actors

A single authentication endpoint can serve many different principals — human users, background agents, third-party integrations — each with distinct key policies.

4

Audit and Rotation Are Non-Negotiable

Scoped keys must be auditable, rotatable, and revocable individually. Centralized key management prevents stale keys from lingering.

5

Design for Compromise from the Start

Assume keys will be exposed. Least privilege, short lifetimes, and narrow scopes limit what an attacker can do if a key is stolen.

One auth surface, many actors

We use the same auth middleware for humans and machines, but the token metadata differs. A CI key carries scopes like policies:write and devices:read. A SIEM key gets analytics:read and audit:read. An AI editor key might only get threats:read and policies:write.

Fingerprinting every call

Every audit log row records the api_key_id that made the call, not just the user who created it. That means when Claude blocks a domain through MCP, the log shows it was the agent key — traceable, revocable, and scoped.

Rotation and expiry

Scoped keys support expiry dates and last-used timestamps. We surface stale keys in the dashboard so security teams can revoke what they forgot.
